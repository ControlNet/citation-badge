# Google Scholar publication metadata boundary

- Date: 2026-08-31
- `main.py` calls `scholarly.fill(author_seed, sortby="year")` with no section filter. In `scholarly 1.7.11`, this fills every author section: basics, indices, counts, coauthors, publications, and public access.
- The generated `citation.json` deliberately discards most of the returned object. Author output currently retains citation metrics only. Publication output currently retains only `author_pub_id`, `title`, `year`, and `citations`.
- Fields already available from the existing author-profile fetch, without one detail request per paper, include author `scholar_id`, `name`, `affiliation`, `organization`, `email_domain`, `url_picture`, `homepage`, `interests`, `public_access`, and `coauthors`. Lightweight publication entries may include `bib.citation`, `cites_id`, `citedby_url`, and `public_access` in addition to the four fields currently emitted. Optional fields must be read with `.get()` because Scholar profiles are inconsistent.
- "No additional requests" above is relative to the current `sections=[]` behavior. That behavior already requests the complete coauthor list when available and public-access mandate pages. If author fill is later restricted to `basics`, `indices`, `counts`, and `publications`, `coauthors` and per-publication `public_access` will no longer be available.
- For each lightweight author-page publication, the useful raw output boundary is: `author_pub_id`, `bib.title`, `bib.pub_year`, `bib.citation`, `num_citations`, optional `cites_id`, optional `citedby_url`, and optional `public_access`. `filled`, `source`, and `container_type` are library bookkeeping and should not be published as downstream content fields.
- Project schema decision: expose the lightweight publication entry's `bib.citation` value as `publications[].venue`. This is a display-oriented venue string and can include journal/conference name, volume, issue, pages, and year; it is not a normalized venue name. Missing values are emitted as an empty string for compatibility with the existing publication fields.
- Useful request-free derived fields include a canonical Scholar profile URL from the resolved `scholar_id`, a Scholar publication detail URL from `author_pub_id`, the publication-id suffix after `:`, total publication count, and normalized absolute cited-by URLs. These are conveniences, not additional Scholar metadata.
- Per-publication `public_access` must be nullable/omitted when absent. Absence means Scholar did not classify the entry in the mandate list; it must not be coerced to `false`.
- An author-page publication entry does not preserve the publication author list in this version of `scholarly`; the parser only preserves its second gray metadata line as `bib.citation`.
- Calling `scholarly.fill(pub)` on each author publication opens the publication detail page and may add full title, authors/inventors, journal or conference, volume, issue (`bib.number`), pages, publisher, publication year, description/abstract, `pub_url`, `eprint_url`, `cites_id`, `citedby_url`, per-paper `cites_per_year`, and related-article URL. Availability varies per publication. DOI is not a first-class field parsed from author publication detail pages by `scholarly 1.7.11`.
- Per-publication fill changes request cost from roughly profile pages plus pagination to one additional Google Scholar detail request per publication. With hourly refreshes and a 180-second per-profile timeout, filling every paper increases timeout, rate-limit, CAPTCHA, and IP-blocking risk substantially.
- Recommended architecture for a downstream publication list: publish lightweight metadata on every hourly citation refresh; enrich only new or changed publications into a persistent cache on a slower schedule, preserving previous detail metadata when an individual detail fetch fails. Keep manually curated fields such as DOI, canonical URL, selected/featured status, display authors, and venue naming outside Scholar-owned refresh data.
